Introduction

This is the second worked example. If you have not seen the first one, Tiles explains how tile data gets into video memory, and its helper routines are used here too.

On the ZX Spectrum, moving graphics are drawn in software, with pre-shifted copies and masks. The Game Boy does it in hardware. It has a table of 40 sprites (the OAM, at $FE00), each 4 bytes: a Y position, an X position, a tile number and some attributes. The screen hardware draws the sprites on top of the background for you, and shade 0 is transparent, so there is no separate mask. A character bigger than one sprite is built from several, side by side. The Sprite Editor does that split for you.

Exporting from the Editor

  1. In the Sprite Editor, set the sprite size in tiles (the hero is 2×2 tiles, 16×16 pixels) and the OBJ size. The example uses 8×16: each hardware sprite is a column of two tiles, so the hero is two sprites. In 8×8 mode it would be four.
  2. Draw each frame, give it a duration (in 1/60 s ticks) and press Play to preview. Choose the palette (OBP0 or OBP1) and whether the sprite is drawn behind the background.
  3. Click Export RGBDS (.asm) and name the file hero. Load hero_sprite.json with Load project to see the sprite below in the editor.

Tiles that are completely empty are not exported, and no sprite is created for them.

The Exported Data: hero.asm

[[file sprite/hero.asm]]
  • hero_tiles is the tile data of all frames, one after another. Sprites and the background share the tile memory at $8000; the sprite's tile numbers count from the first tile you load.
  • hero_frames is a table of pointers, one per frame. Each points to a list: first the number of sprites, then for each sprite four bytes: y offset, x offset, tile number, attributes. The offsets are from the top-left corner of the whole character. In 8×16 mode the tile number of a sprite is the first of its two tiles.
  • hero_durations holds how many frames (1/60 s) each animation frame stays on screen.
  • The attribute byte holds the palette (bit 4), flip bits (6 and 5) and the priority bit (bit 7). The editor sets the palette and priority you chose; flipping is up to the program, which can OR a flip bit into the byte when it copies it.

The Program: sprite_demo.asm

Setting up

The tiles are copied to $8000 with the LCD off, as in the first example. The sprite table contains random bytes when the console starts, so the program also switches all 40 sprites off by filling it with zeros (a sprite with Y = 0 is off the top of the screen). It then sets rLCDC bit 2 (LCDCF_OBJ16) to select 8×16 sprites, since that is how the hero was exported, and LCDCF_OBJON to show sprites. There is no LCDCF_BGON, so the background is off and the screen is plain white behind the hero.

The main loop

Every pass starts with WaitFrame, which returns at the start of VBlank. That is the time the sprite table can safely be written. The rest of the frame is for working out what happens next.

Writing the sprite table

DrawSprite looks up the current frame in hero_frames and copies each entry to the sprite table, adding the hero's position. The hardware subtracts 16 from every Y and 8 from every X, so that a sprite can slide in from off screen; the program adds them back. When it has copied the entries it clears the rest of the table, because the next frame may have fewer sprites.

[[part sprite/sprite_demo.asm | ; Write the OAM entries | INCLUDE "util.inc"]]

Animating and moving

Animate counts down a timer; when it reaches zero it moves to the next frame (wrapping at HERO_FRAME_COUNT) and loads that frame's duration from hero_durations. Move reads the keys that ReadJoypad stored in wJoypad and changes the position by one pixel per frame.

Assembling and Running

[[text]] make sprite/sprite_demo.gb # assemble, link and fix the header make run-sprite/sprite_demo # ...and open it in mGBA [[/text]]

The hero walks on the spot; use the direction keys (arrow keys in mGBA) to move it. The program does not stop it leaving the screen: try adding limits to Move.

Things to try: draw a third frame in the editor and export again (only the file changes, not the program); switch the sprite to OBP1 and set rOBP1 in the program; set the behind background option, turn the background on and see the hero disappear behind anything that is not shade 0.
