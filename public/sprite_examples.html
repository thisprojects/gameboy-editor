Sprites: Animating an Exported Sprite

From the Sprite Editor to a moving hero on a Game Boy screen
DOT MATRIX · 160 × 144 · 4 SHADES
Examples: Tiles Sprites Background Font Level Music · Game Boy Assembly Introduction

Introduction

This is the second worked example. If you have not seen the first one, Tiles explains how tile data gets into video memory, and its helper routines are used here too.

The Game Boy draws moving graphics in hardware. It has a table of 40 sprites (the OAM, at $FE00), each 4 bytes: a Y position, an X position, a tile number and some attributes. The screen hardware draws the sprites on top of the background for you, and shade 0 is transparent, so there is no separate mask. A character bigger than one sprite is built from several, side by side. The Sprite Editor does that split for you.

Exporting from the Editor

  1. In the Sprite Editor, set the sprite size in tiles (the hero is 2×2 tiles, 16×16 pixels) and the OBJ size. The example uses 8×16: each hardware sprite is a column of two tiles, so the hero is two sprites. In 8×8 mode it would be four.
  2. Draw each frame, give it a duration (in 1/60 s ticks) and press Play to preview. Choose the palette (OBP0 or OBP1) and whether the sprite is drawn behind the background.
  3. Click Export RGBDS (.asm) and name the file hero. Load hero_sprite.json with Load project to see the sprite below in the editor.

Tiles that are completely empty are not exported, and no sprite is created for them.

The Exported Data: hero.asm

; hero - 2 frame(s), 8 tile(s)
; Each frame: db entry_count, then per entry: db y_offset, x_offset, tile, attr
; Add 16 to Y and 8 to X (plus your position) when writing to OAM. Tile indices are relative to
; the first tile you load. Flip flags can be OR-ed into attr at runtime. Durations are in 1/60 s ticks.

DEF HERO_FRAME_COUNT EQU 2
DEF HERO_TILE_COUNT EQU 8

SECTION "hero_sprite", ROM0

hero_tiles::
    db $07, $07, $0F, $0F, $08, $0F, $0A, $0F, $08, $0F, $07, $07, $18, $1F, $28, $3F ; tile 0
    db $28, $3F, $38, $3F, $08, $0F, $0D, $0F, $0A, $0E, $1A, $1E, $1C, $1C, $00, $00 ; tile 1
    db $E0, $E0, $F0, $F0, $10, $F0, $50, $F0, $10, $F0, $E0, $E0, $18, $F8, $14, $FC ; tile 2
    db $14, $FC, $1C, $FC, $10, $F0, $B0, $F0, $50, $70, $58, $78, $38, $38, $00, $00 ; tile 3
    db $07, $07, $0F, $0F, $08, $0F, $0A, $0F, $08, $0F, $07, $07, $18, $1F, $28, $3F ; tile 4
    db $28, $3F, $38, $3F, $08, $0F, $0D, $0F, $05, $07, $05, $07, $07, $07, $00, $00 ; tile 5
    db $E0, $E0, $F0, $F0, $10, $F0, $50, $F0, $10, $F0, $E0, $E0, $18, $F8, $14, $FC ; tile 6
    db $14, $FC, $1C, $FC, $10, $F0, $B0, $F0, $A0, $E0, $A0, $E0, $70, $70, $00, $00 ; tile 7
hero_tiles_end::

hero_frames::
    dw hero_frame0
    dw hero_frame1

hero_durations::
    db 12, 12

hero_frame0:
    db 2
    db 0, 0, 0, $00
    db 0, 8, 2, $00
hero_frame1:
    db 2
    db 0, 0, 4, $00
    db 0, 8, 6, $00
  • hero_tiles is the tile data of all frames, one after another. Sprites and the background share the tile memory at $8000; the sprite's tile numbers count from the first tile you load.
  • hero_frames is a table of pointers, one per frame. Each points to a list: first the number of sprites, then for each sprite four bytes: y offset, x offset, tile number, attributes. The offsets are from the top-left corner of the whole character. In 8×16 mode the tile number of a sprite is the first of its two tiles.
  • hero_durations holds how many frames (1/60 s) each animation frame stays on screen.
  • The attribute byte holds the palette (bit 4), flip bits (6 and 5) and the priority bit (bit 7). The editor sets the palette and priority you chose; flipping is up to the program, which can OR a flip bit into the byte when it copies it.

The Program: sprite_demo.asm

Setting up

The tiles are copied to $8000 with the LCD off, as in the first example. The sprite table contains random bytes when the console starts, so the program also switches all 40 sprites off by filling it with zeros (a sprite with Y = 0 is off the top of the screen). It then sets rLCDC bit 2 (LCDCF_OBJ16) to select 8×16 sprites, since that is how the hero was exported, and LCDCF_OBJON to show sprites. There is no LCDCF_BGON, so the background is off and the screen is plain white behind the hero.

Start:
    call LcdOff

    ld hl, hero_tiles
    ld de, VRAM_TILES
    ld bc, hero_tiles_end - hero_tiles
    call CopyBytes

    ld hl, OAM_RAM           ; the sprite table starts with random data: switch all 40 sprites off
    ld bc, OAM_SIZE
    xor a
    call FillBytes

    xor a
    ld [wFrame], a
    ld a, 72
    ld [wX], a
    ld a, 64
    ld [wY], a
    ld a, [hero_durations]   ; the first frame stays for hero_durations[0] frames
    ld [wTimer], a

    ld a, %11100100
    ldh [rOBP0], a           ; sprite palette (colour 0 is transparent)
    ld a, LCDCF_ON | LCDCF_OBJ16 | LCDCF_OBJON
    ldh [rLCDC], a           ; the Sprite Editor exported 8x16 sprites: turn on 8x16 mode

The main loop

Every pass starts with WaitFrame, which returns at the start of VBlank. That is the time the sprite table can safely be written. The rest of the frame is for working out what happens next.

.loop:
    call WaitFrame
    call DrawSprite          ; the sprite table (OAM) may only be written during VBlank
    call ReadJoypad
    call Move
    call Animate
    jr .loop

Writing the sprite table

DrawSprite looks up the current frame in hero_frames and copies each entry to the sprite table, adding the hero's position. The hardware subtracts 16 from every Y and 8 from every X, so that a sprite can slide in from off screen; the program adds them back. When it has copied the entries it clears the rest of the table, because the next frame may have fewer sprites.

; Write the OAM entries of the current frame, moved to the sprite's position.
; Each entry in the export is 4 bytes: y offset, x offset, tile, attributes.
DrawSprite:
    ld a, [wFrame]
    add a, a                 ; hero_frames holds 2-byte pointers
    ld e, a
    ld d, 0
    ld hl, hero_frames
    add hl, de
    ld a, [hl+]
    ld h, [hl]
    ld l, a                  ; HL = the entries of this frame
    ld a, [hl+]              ; first byte: how many entries
    ld b, a
    ld de, OAM_RAM
    or a
    jr z, .clearRest
.entry:
    ld a, [wY]
    add a, [hl]              ; + y offset
    add a, 16                ; the hardware subtracts 16 from Y ...
    ld [de], a
    inc hl
    inc de
    ld a, [wX]
    add a, [hl]              ; + x offset
    add a, 8                 ; ... and 8 from X
    ld [de], a
    inc hl
    inc de
    ld a, [hl+]              ; tile number
    ld [de], a
    inc de
    ld a, [hl+]              ; attributes (palette, priority, flip)
    ld [de], a
    inc de
    dec b
    jr nz, .entry
.clearRest:                  ; switch off every sprite we did not use
    ld a, e
    cp OAM_SIZE
    ret nc
    xor a
    ld [de], a
    inc de
    jr .clearRest

Animating and moving

Animate counts down a timer; when it reaches zero it moves to the next frame (wrapping at HERO_FRAME_COUNT) and loads that frame's duration from hero_durations. Move reads the keys that ReadJoypad stored in wJoypad and changes the position by one pixel per frame.

; Move the sprite one pixel per frame in the direction of the pressed keys
Move:
    ld a, [wJoypad]
    ld b, a
    bit PADB_RIGHT, b
    jr z, .notRight
    ld hl, wX
    inc [hl]
.notRight:
    bit PADB_LEFT, b
    jr z, .notLeft
    ld hl, wX
    dec [hl]
.notLeft:
    bit PADB_DOWN, b
    jr z, .notDown
    ld hl, wY
    inc [hl]
.notDown:
    bit PADB_UP, b
    ret z
    ld hl, wY
    dec [hl]
    ret

; Count down the frame timer and switch to the next animation frame when it runs out
Animate:
    ld a, [wTimer]
    dec a
    ld [wTimer], a
    ret nz
    ld a, [wFrame]
    inc a
    cp HERO_FRAME_COUNT
    jr c, .noWrap
    xor a                    ; after the last frame, start again
.noWrap:
    ld [wFrame], a
    ld e, a
    ld d, 0
    ld hl, hero_durations
    add hl, de
    ld a, [hl]
    ld [wTimer], a
    ret

; hero_durations and HERO_FRAME_COUNT. Use the direction keys to move the hero.

Assembling and Running

make sprite/sprite_demo.gb       # assemble, link and fix the header
make run-sprite/sprite_demo      # ...and open it in mGBA

The hero walks on the spot; use the direction keys (arrow keys in mGBA) to move it. The program does not stop it leaving the screen: try adding limits to Move.

Things to try: draw a third frame in the editor and export again (only the file changes, not the program); switch the sprite to OBP1 and set rOBP1 in the program; set the behind background option, turn the background on and see the hero disappear behind anything that is not shade 0.

The Same Thing in C with GBDK

If you prefer C, Export C writes hero.h with the tiles, one array per frame (an entry count, then Y offset, X offset, tile and attribute for each entry), the frame table hero_frames and hero_durations. With GBDK-2020 the tiles are loaded with set_sprite_data and each entry becomes one hardware sprite. (The programs in these examples are the RGBDS ones; the C below follows the GBDK documentation but is not compiled or run by the test script.)

#include <gb/gb.h>
#include "hero.h"

static void draw_frame(unsigned char f, unsigned char x, unsigned char y) {
    const unsigned char *p = hero_frames[f];
    unsigned char n = *p++;
    for (unsigned char i = 0; i < n; i++, p += 4) {
        set_sprite_tile(i, p[2]);
        set_sprite_prop(i, p[3]);
        move_sprite(i, x + p[1] + 8, y + p[0] + 16);   /* OAM coordinates are offset by 8 and 16 */
    }
}

void main(void) {
    set_sprite_data(0, HERO_TILE_COUNT, hero_tiles);
    SHOW_SPRITES;
    draw_frame(0, 80, 72);
}

When the sprite uses a different frame count, hide the sprites a frame no longer needs with move_sprite(i, 0, 0).
