Tiles: Displaying Exported Tiles

From the Tile Editor to pixels on a Game Boy screen
DOT MATRIX · 160 × 144 · 4 SHADES
Examples: Tiles Sprites Background Font Level Music · Game Boy Assembly Introduction

Introduction

These pages are worked examples, one per editor. Each one takes the file the editor exports and shows it on a real (emulated) Game Boy, with a small assembly program you can read, change and reuse. If you have not written Game Boy assembly before, read An Introduction to Game Boy Assembly Language first.

Every program in these examples is assembled with RGBDS and run on an emulated Game Boy by examples/verify_examples.py, which compares the emulated screen (or sound) with what the editor says it should be. The programs live in the examples/ folder of the editor project, next to the editor files they use: you can load forest_tiles.json into the Tile Editor with Load project and see exactly the tiles used below.

The Game Boy has no screen memory to draw pixels into. Everything it shows is made of 8×8 pixel tiles. Each pixel has one of 4 shades, so a tile takes 2 bits per pixel: 16 bytes. The tiles live in video memory (VRAM) from $8000; there is room for 384. The background is then a grid of tile numbers (the tile map), and the hardware draws the tile each number points to. This page shows the first half of that story: getting tiles into VRAM and onto the screen.

Exporting from the Editor

  1. In the Tile Editor, draw your tiles. The canvas is a grid of tiles numbered left to right, top to bottom (turn on Show tile numbers); the example uses a 4×2 grid, so 8 tiles.
  2. Click Export RGBDS (.asm) and name the file forest. You get forest.asm. (Export C gives a GBDK header, Export .2bpp the raw tile bytes.)
  3. Put forest.asm next to your program and INCLUDE it, as tile_viewer.asm below does.

Trailing blank tiles are left out of the export, so the data is only as big as the tiles you actually drew.

The Exported Data: forest.asm

; forest - 8 tile(s), Game Boy 2bpp
; Copy to VRAM with e.g. a memcpy to $8000 (sprites/BG) or $9000 (BG signed)

DEF FOREST_TILE_COUNT EQU 8

SECTION "forest_tiles", ROM0

forest_tiles::
    db $00, $00, $00, $00, $00, $00, $00, $00, $00, $00, $00, $00, $00, $00, $00, $00 ; tile 0
    db $FF, $FF, $84, $FF, $84, $FF, $FF, $FF, $21, $FF, $21, $FF, $FF, $FF, $21, $FF ; tile 1
    db $00, $00, $22, $00, $54, $00, $00, $00, $88, $00, $52, $00, $00, $00, $22, $00 ; tile 2
    db $00, $00, $00, $CC, $00, $33, $00, $00, $00, $CC, $00, $33, $00, $00, $00, $00 ; tile 3
    db $FF, $FF, $81, $FF, $BD, $FF, $BD, $FF, $BD, $FF, $BD, $FF, $81, $FF, $FF, $FF ; tile 4
    db $18, $18, $3C, $3C, $7E, $7E, $FF, $FF, $7E, $7E, $00, $18, $00, $18, $00, $18 ; tile 5
    db $00, $00, $10, $00, $38, $10, $12, $00, $4E, $04, $E4, $40, $40, $0C, $00, $0C ; tile 6
    db $55, $00, $AA, $00, $55, $00, $AA, $00, $55, $00, $AA, $00, $55, $00, $AA, $00 ; tile 7
forest_tiles_end::

The file defines FOREST_TILE_COUNT (how many tiles there are), the label forest_tiles where the data starts and forest_tiles_end just after it, so forest_tiles_end - forest_tiles is the size in bytes. It is a SECTION of its own: the linker decides where in the ROM it goes.

How a tile is stored

Each row of 8 pixels takes two bytes. The first byte holds the low bit of every pixel's shade, the second the high bit, with the leftmost pixel in bit 7. Take the second row of the brick tile (tile 1), drawn as #oooo#oo where # is shade 3 and o shade 2:

pixel          #  o  o  o  o  #  o  o
shade          3  2  2  2  2  3  2  2
low bit        1  0  0  0  0  1  0  0   = $84
high bit       1  1  1  1  1  1  1  1   = $FF

That is the $84, $FF pair in the data. The Game Boy has no colour in each pixel, just a shade number from 0 to 3; what shade you actually see comes from a palette register (below).

The Program: tile_viewer.asm

Copying the tiles to VRAM

VRAM can only be written freely while the screen hardware is not reading it, so the program switches the LCD off first (LcdOff waits for the start of VBlank, the gap between two frames, because switching off at any other moment can damage a real screen). Then it copies the tile data to $8000 (VRAM_TILES): tile 0 will be at $8000, tile 1 at $8010, and so on.

Start:
    call LcdOff              ; VRAM can only be written freely while the LCD is off

    ; Copy the tile data to the start of tile memory: tile 0 lives at $8000, tile 1 at $8010, ...
    ld hl, forest_tiles
    ld de, VRAM_TILES
    ld bc, forest_tiles_end - forest_tiles
    call CopyBytes

Filling the tile map

The background map is a 32×32 grid of tile numbers at $9800 (VRAM_MAP). The program first fills it with tile 0, a blank tile, then writes tile numbers 0 to 7 in one row.

    ; Clear the background map: every cell shows tile 0 (the blank tile)
    ld hl, VRAM_MAP
    ld bc, VRAM_MAP_W * VRAM_MAP_W
    xor a
    call FillBytes

    ; Put tile 0, 1, 2 ... in a row across the middle of the screen
    ld hl, VRAM_MAP + 8 * VRAM_MAP_W + 6
    xor a                    ; A = tile number to show
    ld b, FOREST_TILE_COUNT
.showTiles:
    ld [hl+], a
    inc a
    dec b
    jr nz, .showTiles

Palette and switching the screen on

rBGP maps the four shades in the tile data to the four shades the screen can show: two bits for each, shade 0 in the lowest bits. %11100100 means “shade 0 shows as 0, 1 as 1, 2 as 2, 3 as 3”, so the tiles look as drawn. Try %00011011 to invert them. Finally rLCDC turns the LCD on with the background enabled and the tile data at $8000; without LCDCF_BG8000 the hardware would look for background tiles at $8800 instead.

    ld a, %11100100          ; palette: colour 0 = lightest ... colour 3 = darkest
    ldh [rBGP], a
    ld a, LCDCF_ON | LCDCF_BG8000 | LCDCF_BGON
    ldh [rLCDC], a           ; LCD on, background on, tile data at $8000

.forever:
    halt
    nop
    jr .forever

Complete Source

; tile_viewer.asm - show the tiles exported from the Tile Editor
;
; Export "forest" from the Tile Editor (Export RGBDS) and put forest.asm next to this file.
; It provides forest_tiles (the tile data), forest_tiles_end and FOREST_TILE_COUNT.

INCLUDE "hardware.inc"
INCLUDE "forest.asm"

SECTION "Header", ROM0[$100]
    nop
    jp Start
    ds $150 - @, 0           ; room for the cartridge header (rgbfix fills it in)

SECTION "Main", ROM0[$150]
Start:
    call LcdOff              ; VRAM can only be written freely while the LCD is off

    ; Copy the tile data to the start of tile memory: tile 0 lives at $8000, tile 1 at $8010, ...
    ld hl, forest_tiles
    ld de, VRAM_TILES
    ld bc, forest_tiles_end - forest_tiles
    call CopyBytes

    ; Clear the background map: every cell shows tile 0 (the blank tile)
    ld hl, VRAM_MAP
    ld bc, VRAM_MAP_W * VRAM_MAP_W
    xor a
    call FillBytes

    ; Put tile 0, 1, 2 ... in a row across the middle of the screen
    ld hl, VRAM_MAP + 8 * VRAM_MAP_W + 6
    xor a                    ; A = tile number to show
    ld b, FOREST_TILE_COUNT
.showTiles:
    ld [hl+], a
    inc a
    dec b
    jr nz, .showTiles

    ld a, %11100100          ; palette: colour 0 = lightest ... colour 3 = darkest
    ldh [rBGP], a
    ld a, LCDCF_ON | LCDCF_BG8000 | LCDCF_BGON
    ldh [rLCDC], a           ; LCD on, background on, tile data at $8000

.forever:
    halt
    nop
    jr .forever

    INCLUDE "util.inc"

The Helper Routines: util.inc

Every example INCLUDEs two small files from examples/common/. hardware.inc gives names to the hardware registers (it extends the file of the same name from the book). util.inc has the routines the examples share. They are used on the other pages too.

; =============================================================
; util.inc - small helper routines shared by the editor examples
; =============================================================
; INCLUDE this file after your own code. It needs hardware.inc.
;
;   WaitFrame    - wait for the start of the next VBlank (one call per frame)
;   LcdOff       - turn the LCD off (VRAM can then be written freely)
;   CopyBytes    - copy BC bytes from HL to DE
;   FillBytes    - fill BC bytes at HL with A
;   ReadJoypad   - read the buttons into wJoypad (1 = pressed, see PADB_* in hardware.inc)

SECTION "UtilVars", WRAM0
wJoypad: DS 1

SECTION "Util", ROM0

; Wait until the start of the next VBlank. Calling this once per loop gives you exactly one pass per frame.
WaitFrame:
.leaveVBlank:
    ldh a, [rLY]
    cp 144
    jr nc, .leaveVBlank      ; still in VBlank from last time: wait for it to end
.waitVBlank:
    ldh a, [rLY]
    cp 144
    jr c, .waitVBlank        ; draw time: wait for line 144, the start of VBlank
    ret

; The LCD may only be switched off during VBlank, or the screen hardware can be damaged.
LcdOff:
.waitVBlank:
    ldh a, [rLY]
    cp 144
    jr c, .waitVBlank
    xor a
    ldh [rLCDC], a
    ret

; HL = source, DE = destination, BC = number of bytes (not zero)
CopyBytes:
    ld a, [hl+]
    ld [de], a
    inc de
    dec bc
    ld a, b
    or c
    jr nz, CopyBytes
    ret

; A = value, HL = destination, BC = number of bytes (not zero)
FillBytes:
    ld d, a
.loop:
    ld a, d
    ld [hl+], a
    dec bc
    ld a, b
    or c
    jr nz, .loop
    ret

; Reads the direction keys and buttons into wJoypad. The hardware reports 0 for a pressed key, so the
; value is inverted to make 1 mean pressed. Bits 0-3: right, left, up, down. Bits 4-7: A, B, select, start.
ReadJoypad:
    ld a, P1F_GET_DPAD
    ldh [rP1], a
    ldh a, [rP1]             ; read a few times: the lines need a moment to settle
    ldh a, [rP1]
    ldh a, [rP1]
    cpl
    and $0F
    ld b, a                  ; B = direction keys
    ld a, P1F_GET_BTN
    ldh [rP1], a
    ldh a, [rP1]
    ldh a, [rP1]
    ldh a, [rP1]
    cpl
    and $0F
    swap a                   ; buttons go in the upper nibble
    or b
    ld [wJoypad], a
    ld a, P1F_GET_NONE
    ldh [rP1], a
    ret

Two details worth knowing. The interrupt vectors: when an interrupt happens the CPU jumps to $40, $48, $50, $58 or $60. The examples do not use interrupts, but the linker may put data in the first bytes of the ROM, so the file reserves those addresses with a reti. One frame per loop: WaitFrame waits for the screen to leave VBlank and come back, so a loop that calls it once runs exactly once per frame, 60 times a second.

Assembling and Running

You need RGBDS (0.5 or later; brew install rgbds on a Mac) and an emulator such as mGBA. In the examples folder:

make tiles/tile_viewer.gb       # assemble, link and fix the header
make run-tiles/tile_viewer      # ...and open it in mGBA

Or by hand, which is all make does:

rgbasm -I common/ -I tiles/ -o tile_viewer.o tiles/tile_viewer.asm
rgblink -n tile_viewer.sym -o tile_viewer.gb tile_viewer.o
rgbfix -v -p 0xFF -t TILEVIEWER tile_viewer.gb

rgbfix fills in the cartridge header (the Nintendo logo and checksums the console checks) which the program leaves as zeros. To use your own tiles, export them as forest.asm (or change the INCLUDE and the label names) and run the same commands.

The Same Thing in C with GBDK

If you prefer C, Export C writes forest.h with the same data and FOREST_TILE_COUNT. With GBDK-2020 it is loaded with set_bkg_data. (The programs in these examples are the RGBDS ones; the C below follows the GBDK documentation but is not run by the test script.)

#include <gb/gb.h>
#include "forest.h"

void main(void) {
    set_bkg_data(0, FOREST_TILE_COUNT, forest_tiles);   /* tiles to VRAM from tile 0 */
    unsigned char row[FOREST_TILE_COUNT];
    for (unsigned char i = 0; i < FOREST_TILE_COUNT; i++) row[i] = i;
    set_bkg_tiles(6, 8, FOREST_TILE_COUNT, 1, row);      /* one row of the background map */
    SHOW_BKG;
}
